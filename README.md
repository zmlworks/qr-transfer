# QR分割転送 (電波を使わないデータ受け渡し) — QR Split Transfer

テキストや小さなファイルを、**電波を一切使わず**に画面とカメラだけで受け渡すアプリです。
送信側がデータを分割して QR コードのアニメーションとして表示し、受信側がカメラで読み取って復元・検証します。
スマホ ⇄ スマホ のほか、PC のブラウザ (付属の `web/sender.html`) → スマホ も可能です。

> このアプリは AI アシスタント **Grok Bot** が設計・実装しました (zmlworks の依頼による)。

## 使い方
- **送信**: テキストを入力、またはファイルを選ぶ (最大 2 MB) → チャンクサイズ・速度・誤り訂正を選んで「送信開始」。
  他アプリの「共有」から直接送ることもできます。表示中は画面を最大輝度に保ちます。
  0.2.0 からは **QR を 2 枚同時に** 表示します (縦持ち: 上下、横持ち: 左右。上/左 = 偶数番、下/右 = 奇数番)。
  受信側が 0.1.0 のときは「2枚同時に表示」をオフにしてください。
- **受信**: 送信側の画面に、**2 枚とも入るように** カメラを向けるだけ (1 枚のカメラ画像から 2 つとも読みます)。
  進捗 (n / 総数)、欠けているチャンク (例 `欠落: 3, 7-9`) とマス目表示。揃うと CRC-32 を検証し、テキストはコピー、
  ファイルは保存 (SAF) / 共有できます。
- **PC → スマホ**: `web/sender.html` をブラウザで開く (オフラインの単一ファイル、外部読み込みなし、CSP で通信禁止)。
  横長の画面では左右に 2 枚並べます。送信中は設定欄を畳み、2 枚が画面に収まるようにします。
  アプリのトップ画面の「PC用Web送信機を共有」から、この HTML をスマホから PC へ渡すこともできます。

## 確認音 (acknowledgment tones) — 2 スロット方式
| 音 | 意味 |
|---|---|
| **1500 Hz** 100 ms | スロット A (上/左のコード = 偶数番) を読んだ |
| **2200 Hz** 100 ms | スロット B (下/右のコード = 奇数番) を読んだ |
| **2700 Hz** 450 ms | 全チャンクが揃い CRC-32 も一致 (完了) |

- 受信側は、各スロットで **前回と違う番号** を読んだら、その番号の偶奇で A か B を鳴らします (読み済みの重複でも鳴らす
  ので送信側は先へ進めます)。同じコードが表示され続けたら 1 秒ごとに鳴らし直します (確認音が届かなかった場合の再送対策)。
  A と B が同時に必要なときは重ならないよう順番に鳴らします。完了後も同じ転送のコードが見えている間は、2 秒ごとに完了音を
  繰り返します (送信側が完了音を聞き逃しても止まれるように)。
- 送信側で「受信側の確認音で進める (マイク)」をオンにすると (Web 送信機では既定でオン):
  1. 各スロットは **自分の音が聞こえた瞬間に次へ** 進みます。上下は独立なので、1 枚表示の約 2 倍の速さになります。
  2. 音が来なければ **適応タイムアウト** (実測の確認音の遅れ × 2.5 + 200 ms、0.5〜4 秒) で次へ進み、未確認のチャンクは
     次の周回で再送します。切り替え直後 150 ms 以内に届いた音は、前に表示していたコードへの確認とみなします。
  3. 全部確認済みなのに完了音がなければ、2.5 秒後に全体をもう一周 (誤検出の確認を取り消すため)。完了音で停止。
- マイクが使えない・許可されないときは、2 枚を設定速度で単純ループします (受信は問題なくできます)。

### 周波数の選び方 (Grok Bot より)
- **1.2〜3 kHz に収める**: スマホの小さなスピーカーは 1 kHz 未満がほとんど出ず、3〜4 kHz 以上は機種差が大きい。
  マイク側 (16 kHz サンプリング) もこの帯域は素直で、電源ハム (50/60 Hz とその倍音) や話し声の主成分 (〜1 kHz) より上です。
- **互いに 500 Hz 以上離す**: 16 ms ブロック (256 点 @16 kHz) の Goertzel は 1 ビン 62.5 Hz、ハン窓の主ローブは ±125 Hz。
  500 Hz = 8 ビン離れていれば漏れは −40 dB 以下で、取り違えません。
- **倍音に重ねない**: スピーカーの歪みで出る 2 倍・3 倍音 (A → 3000/4500 Hz、B → 4400 Hz) が他の音 (2200/2700 Hz) に
  近くならない組み合わせにしました。0.1.0 の音 (1900/2850 Hz) とも別なので、古い受信機の音を誤って数えません。
- 判定は「その周波数のエネルギーが全体の 40% 以上」かつ最低音量を、A/B は 2 ブロック (32 ms)、完了音は 8 ブロック
  (128 ms) 連続で満たしたら 1 回。話し声・雑音・他のビープでは反応しないことをテストしています。

## プロトコル QT1
```
QT1:<ID 8桁hex>:<番号 0始まり>:<総数>:<CRC32 8桁hex>:<Base45データ>
エンベロープ = u8 版(1) | u8 フラグ(bit0 ファイル, bit1 DEFLATE) | u16 名前長 | 名前(UTF-8) | 本体
```
- CRC-32 は**元データ全体** (圧縮前) のもの。全フレームに入っているので、どのフレームから読み始めても転送を識別できます。
- 文字はすべて QR の「英数字モード」の 45 文字に収まります。

## なぜこの設計にしたか (Grok Bot より)
いちばん効いた工夫は **Base45 + QR 英数字モード** です。QR の英数字モードは 1 文字 5.5 ビットで、Base45 は
2 バイトを 3 文字にするので効率約 97%。Base64 をバイトモードで載せる (75%) より、同じ QR の大きさで約 3 割多く運べます。
ヘッダも英数字だけで作り、毎フレームに ID・総数・CRC を入れて「途中から見ても分かる」ようにしました (噴水符号のような
冗長化も考えましたが、まずは単純で検証しやすい方式を選択)。テキストは DEFLATE で圧縮し、効かないときは圧縮しません。
カメラは CameraX ではなく Camera2 を直接使いました。CameraX は AndroidX 一式を引き込み、APK が数 MB 増えるためです。
確認音は「受信側→送信側」の唯一の逆向き通信路で、これも電波を使いません。0.2.0 では「どのコードを読んだか」を
番号の偶奇で表すことで、プロトコル (QT1) を変えずに 2 スロット化しました (受信側はカメラ画像内の位置ではなくフレームの番号から
スロットを決めるので、どの向きで構えても混乱しません)。QR 自体は黒地に白ではなく白地に黒にしています
(反転 QR は読めない読み取り器が多いため)。暗いテーマはその周りだけです。

## Why this design (English, short)
Base45 maps 2 bytes to 3 characters of exactly the QR *alphanumeric* set (5.5 bits/char), ~97 % efficient vs. 75 % for
base64 in byte mode — about 30 % more data per code. Every frame carries ID/total/CRC so reception can start anywhere;
text is DEFLATE-compressed when it helps. Camera2 is used directly (CameraX would pull in AndroidX and add megabytes).
0.2.0 shows two codes at once (top/left = even chunks, bottom/right = odd chunks); the receiver decodes both from one
camera frame and answers with a tone per slot (1500 Hz = A, 2200 Hz = B, 2700 Hz = done), chosen inside 1.2–3 kHz where
phone speakers and microphones behave, ≥ 500 Hz apart and off each other's harmonics. The sender (app and web page)
advances each slot independently on its tone, with an adaptive timeout/resend — about twice the throughput of one code.
The slot is the chunk's parity, so the QT1 protocol is unchanged. Without a microphone both codes simply loop.

## ビルド / テスト
```sh
./gradlew testDebugUnitTest lintDebug assembleDebug assembleRelease
node tools/test-web.js         # Web 送信機の JS (プロトコル・QR・確認音検出・送信スケジューラ) を node で実行し fixture を出力
sh tools/test-web-chrome.sh    # headless Chrome で Web 送信機を表示 → スクショからアプリの FrameDecoder で 2 枚読めるか等
```
JVM テスト: Base45 (RFC 9285)、分割/順不同・重複/再構成/CRC 検証、改ざん検出、ZXing 往復、Web 送信機が作ったフレームと
QR 画像のデコード、**確認音 3 種の検出** (順番に・同時に・雑音下・倍音・話し声風・旧版の音・短すぎる完了音)、
**受信側の鳴らし方** (スロット = 偶奇、重複でも鳴らす、1 秒ごとの再確認、完了音の繰り返し)、
**送信スケジューラ** (スロットの独立進行、遅れて届いた音の扱い、適応タイムアウト、再送、検証周回、手動送り) と
カメラ・スピーカー・マイクを模擬した **転送シミュレーション** (2 枚で 1 枚の約 1.9 倍速、弱いカメラでは確認音方式が
単純ループの約 2.7 倍速)、**1 フレームから 2 枚のデコード** (縦並び・横並び・くっついた配置・位置と大きさのランダム 60 例)、
**JS 版スケジューラと Java 版の完全一致** (node で作ったイベント列を Java で再生)。
Chrome E2E: 2 枚横並び / 縦並び / 1 枚 の画面をアプリのデコーダで読む、偽マイクの音で誤作動しない、
合成した確認音で実際に進み完了音で止まる (ブラウザ内の音声経路)。

## 既知の制限 / Known limitations
- 速度の目安: 確認音あり・2 枚同時で、受信側の読み取り〜確認音の遅れが 0.3〜0.5 秒なら 1 スロット 2〜3 枚/秒 ×2
  ≈ 400 B × 5 枚/秒 ≈ 2 KB/s (シミュレーション上。実機の値は未計測)。上限 2 MB。
- 読み取りはカメラの性能・画面の反射・距離に左右されます。モアレが出るときは少し離すか角度を変えてください。
- 確認音モードは静かな場所向け。スピーカー/マイクの特性や OS の音声処理によっては検出できないことがあります (その場合も単純ループとして動きます)。
- 確認音はスロット (偶奇) しか伝えないため、遅れが非常に大きいと確認を前のコードと取り違えることがあります
  (その場合も、完了音が来なければ全体を再確認する周回で補われます)。
- 片方のスロットの担当分 (偶数番か奇数番) が先に終わると、そのスロットは白表示で待ちます (最後の数枚は 1 枚表示と同じ速さ)。
- 2 枚読むため受信カメラは 1920×1080 を使い、1 フレームのデコードは 1 枚のときより重くなります (古い機種では読み取り間隔が延びます)。
- 受信側が 0.1.0 のときは中央の 1 枚しか読めないため、送信側の「2枚同時に表示」をオフにしてください。
- 受信画面は縦向き固定。0.2.0 の 2 枚表示・確認音の往復は実機では未確認です (単体テスト・シミュレーション・Chrome での
  E2E のみ)。スピーカーとマイクの実際の特性で検出できない場合も、タイムアウトで進むので転送自体は続きます。
